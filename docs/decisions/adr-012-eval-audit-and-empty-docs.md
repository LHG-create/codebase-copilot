# ADR-012：当「检索失败」其实是评测在说谎

- 状态：已采纳
- 日期：2026-10-16

## 背景

ADR-011 留下的最后一个结论是：

> 「官方文档域 70.8% 是当前最明显的短板，瓶颈在跨语言语义匹配本身，
>   需要换多语言向量模型或更强的改写策略。」

本轮就是去攻这个短板的。但实测走下来，**结论和这个判断完全不同**：
70.8% 里有一部分根本不是「检索不行」，而是**评测在说谎**——
有 1 条评测项的「标准答案」是一份只有 96 字节的空文件，
另外 3 条对泛化问题使用了过窄的单一答案。

这篇 ADR 记录完整的发现链，以及两个被数据推翻的假设。

## 第一步：诊断失败的 7 条到底是什么

先看官方文档域未命中的 7 条（列表见下），有一个刺眼共性：
**它们全是最经典的主干概念题**，不是冷门细节。

进一步做「正确答案在召回池里排第几」的诊断（`召回池 recall_k=96`，最终取 top4）：

| 未命中项 | 中文路 | 英文路 | RRF 后 | 结论 |
|---|---:|---:|---:|---|
| Spring MVC 控制器方法的参数是怎么绑定的？ | — | #11 | #33 | 在池里，排太后 |
| Vue 3 的响应式系统是怎么实现的？ | #6 | #4 | #14 | 在池里，排太后 |
| LangChain 的 agent 是怎么工作的？ | #3 | — | #14 | 在池里，排太后 |
| LangChain 怎么做检索增强生成 RAG？ | — | #26 | #50 | 在池里，排太后 |
| Spring 的依赖注入有哪几种方式？ | — | — | — | **两路都没召回** |
| FastAPI 的查询参数怎么声明和做校验？ | — | — | — | 在池里 |
| FastAPI 怎么配置跨域 CORS？ | — | — | — | 在池里 |

> **6/7 条不是「没召回」，而是「召回了但排不进 top4」。**
> 正确答案就在 96 条池子里，排在第 14~56 名。这是重排序（rerank）的教科书场景。

## 第二步：rerank 实验 —— 被数据证伪

引入 `dashscope gte-rerank-v2`（cross-encoder 精排），对 48 条候选精排后取 top4。

### 首次实验（当时 `data/codebase/` 副本还是过期的）

| 域 | A 现状 | B 精排（中文 query） | C 精排（英文改写 query） |
|---|---:|---:|---:|
| 项目代码域 文件/符号 | **100.0% / 92.5%** | 100.0% / 85.0% | 92.5% / 80.0% |
| 官方文档域 文件级 | **83.3%** | 79.2% | 75.0% |

**精排在两个域都没有正收益** —— 当时的结论就是「不引入」。

但这一轮还产出了一个更重要的发现：**精排和向量模型「判断一致」** ——
两者都把 `reactivity-in-depth.md`（深入版）排在 `reactivity-fundamentals.md`（基础版）前面。
两个独立模型都这么选，说明**问题不在排序，而在标注本身**。
这一句正是后面「审计评测标注」的直接触发点（见第三步）。

### 数据修正后的复跑（同一脚本、同一模型）

| 域 | A 现状 | B 精排（中文 query） | C 精排（英文改写 query） |
|---|---:|---:|---:|
| 项目代码域 文件/符号 | 97.5% / 80.0% | **100.0% / 85.0%** | 95.0% / 82.5% |
| 官方文档域 文件级 | **83.3%** | 79.2% | 75.0% |

**结论变了**：精排对「项目代码」是**正优化**（文件级 +2.5pp、符号级 +5.0pp），
对「跨语言文档检索」仍是**负优化**（-4.1pp）。

原因也清楚了：本项目代码的注释和 docstring 是**中文**，`gte-rerank-v2` 也是中文强项，
两边语言对齐、判断准确；而中文问题配英文文档时，精排的跨语言匹配能力
不如多语言向量模型（`text-embedding-v3`），反而把正确答案压了下去。

### 最终决策：仍然不引入

它变成了一次「此消彼长」（项目域 +5pp 换文档域 -4.1pp），
而「双域都不牺牲」是本项目的原则；更何况要单独在项目域启用它，
得先准确判断问题属于哪个领域 —— ADR-011 已证实**语义路由只有 65% 准确率**，
判错就是全盘皆输。

> **同一个实验、同一个模型，数据一变结论就变**：首次跑是「两域皆负」，
> 复跑是「一正一负」。这既是教训 5（调参与数据强绑定）的又一例证，
> 也说明**一次实验的结论远不如一个可复现的实验脚本重要** ——
> 脚本留下来了，数据变了重跑就能得到新结论。

`eval_rerank.py` 保留为可复现证据。

## 第三步：回看文档内容 —— 挖到数据层的坑

既然排序不是答案，那就回头核对「标准答案文档本身」。于是看到了这个：

```
======== data/docs/langchain/retrieval.md ========
---
title: Retrieval
sidebarTitle: Retrieval
url: "/oss/deepagents/retrieval"
noindex: true
---
                                    ← 全文到此结束，96 字节
```

**这是「LangChain 怎么做 RAG」的标准答案文档 —— 它是个空壳。**

官网自己都标了 `noindex: true`（不要索引它）。正文一个字都没有，
整篇只剩一段 frontmatter。这意味着：

> 这条评测项**从写下的第一天起就注定失败**，而且跟检索算法
> 一点关系都没有 —— 你无论怎么调参数，都不可能命中一个空文件。

全库扫描后发现有 **16 个同类空壳文档**，其中 **6 个正文完全为 0 字**：

```
langchain/academy.md、changelog-js.md、changelog-py.md、retrieval.md
langgraph/changelog-js.md、changelog-py.md
```

为什么之前没被发现？因为 loader 只做了「内容非空」判断，
而这些文件**有 frontmatter**，`page_content` 非空，于是顺利混进了知识库，
以「标题向量」的形式占据检索候选位。

## 决策一：按「正文长度」过滤空壳文档（数据层）

`app/loader.py` 新增：

- `_body_length(text)`：剥掉 YAML frontmatter 后的正文长度
- `MIN_BODY_CHARS = 200`：低于它视为空壳，不入库
-  `nav-*.adoc` 前缀排除（Spring 文档里的纯导航片段）

**阈值 200 是数据选出来的**，不是拍脑袋：实测被挡掉的全是
导航页 / 索引页 / 团队页 / 合作伙伴页；而 254 字的 `langchain/studio.md`、
348 字的 Spring CLI 安装页都完整保留。

效果：**1023 → 945 个文档，9956 → 9920 个片段**。

## 决策二：审计评测标注（评测层）

顺着「标注可能不靠谱」这条线，把 24 条官方文档评测项逐条核对了一遍，
发现 **4 条有问题**：

| # | 问题 | 原标注 | 修正 | 判据 |
|---|---|---|---|---|
| 1 | LangChain 怎么做 RAG？ | `langchain/retrieval.md` | → `langchain/knowledge-base.md` | **原答案文档是 96 字节空壳**，属事实错误 |
| 2 | FastAPI 查询参数怎么声明**和**做校验？ | `query-params.md` | + `query-params-str-validations.md` | 原答案只覆盖「声明」，问题还问了「校验」 |
| 3 | Spring MVC 参数是**怎么绑定**的？ | `ann-methods/arguments.adoc` | + `mvc-data-binding.adoc` | 原答案是「支持哪些参数类型」的清单（what），问题问的是绑定机制（how） |
| 4 | Vue 3 响应式系统是怎么**实现**的？ | `reactivity-fundamentals.md` | + `extras/reactivity-in-depth.md` | 原答案讲 ref/reactive 的用法，问题问的是实现原理 |

第 1 条是**修错**（答案本身是个空文件），第 2~4 条是**单一金标对泛化问题不成立**。

> 反思一下这 3 条是怎么写错的：标注时是**按「文件名像不像」**来挑的
> （"reactivity-fundamentals" 里有 reactivity，"query-params" 里有 query params），
> 而不是**按「文档内容覆不覆盖问题」**来挑的。
> 这是标注方法本身的缺陷，不是手滑。

因此 `eval_retrieval.py` 的 `_hit_file` 支持**可接受答案集合**：
同一问题有多个等价正确答案时，命中任一即算对。同时保留原严格口径，
在 `eval_audit.py` 里做对照。

## 效果：一个不好看但更重要的结论

把两件事的贡献拆开（`eval_audit.py`）：

| 口径 | 索引 | 官方文档域 文件级 |
|---|---|---:|
| 原评测集（严格单标） | 清洗前（9956 片段） | 70.8% |
| 原评测集（严格单标） | **清洗后（9920 片段）** | **70.8%** |
| 新评测集（修正后） | 清洗后 | **83.3%** |

**数据清洗对分数的贡献是 0。+12.5pp 全部来自评测口径修正。**

这个结果不好看，但它比「涨了 12.5pp」诚实得多，而且更有价值：

- **修标注不是「刷分」，是让基线回到真实水平。** 原标注**低估**了系统 ——
  它把「检索挑出了更完整的文档」误判成「检索失败」。
- **数据清洗的价值不在分数上**，而在于它是**治本**的：
  修掉了一个真实缺陷（空壳文档入库），并让未来新增数据源自动免疫同类问题。
- 如果只看最终数字就宣布「优化成功」，那才是真正的自欺欺人。
  **一个 12.5pp 的变化完全可能来自评测口径，而跟系统毫无关系。**

### 项目代码域（未受影响，作为回归对照）

| 策略 | 文件级 | 符号级 | 文件 MRR |
|---|---:|---:|---:|
| 纯向量（旧口径） | 92.5% | 77.5% | 0.833 |
| 混合检索（对照） | 90.0% | 67.5% | 0.792 |
| **线上链路（最终）** | **100.0%** | **92.5%** | **0.952** |

数据清洗与评测修正都没有动这个域 —— 这也说明本轮改动是定向的，没有全局副作用。

## 残余的 4 条：这是能力边界，不是调参问题

修正口径后仍有 4 条未命中，逐条看 top4：

| 问题 | 期望 | 实际 top4 |
|---|---|---|
| FastAPI 怎么配置跨域 CORS？ | `fastapi/tutorial/cors.md` | `spring-framework/webflux-cors.adoc` ×3 + `project/llm.py` |
| Spring 的依赖注入有哪几种方式？ | `beans/dependencies.adoc` | `beans/dependencies/factory-collaborators.adoc` + spring-boot 的 DI 页 |
| LangChain 的 agent 是怎么工作的？ | `langchain/agents.md` | `langgraph/overview.md` + langchain 其他页 |
| LangChain 怎么做 RAG？ | `langchain/knowledge-base.md` | `langgraph/agentic-rag.md` ×3 |

**四条是同一个根因：同一个概念在多个框架下都有文档。**

- CORS 在 FastAPI 和 Spring 里各有一篇，语义几乎重合
- agent 在 LangChain 和 LangGraph 里各有一套说法
- RAG 在 LangChain 和 LangGraph 里各有一套说法

**检索无法判断用户问的是哪一份** —— 这不是调参能解决的，
属于语义检索的能力边界。硬要解，需要的是「领域路由 + 澄清追问」这类
交互层设计，而不是继续在排序上做文章。

**对照实验**：关掉长尾领域先验后，官方文档域仍是 83.3%，同样这 4 条失败。
说明残余失败与领域先验无关（先验确实会把 `project` 域的笔记/源码提到前面，
但没有改变任何一条的命中结果）。

## 端到端验证抓到的两个隐患（都是评测覆盖不到的）

### 隐患一：`data/codebase/` 源码副本早已过期

`data/codebase/` 是项目源码的**手工副本**，供知识库检索「本项目代码」用。
端到端抽查时发现答案里说「渲染出处使用了 `st.expander` 展开组件」，
而 ADR-011 里明明已经把它改成了平铺输出。查下去：

```
21 个源码文件里，16 个与真实源码不一致（第一次自动同步时的统计）
且缺少后来新增的模块：domain.py / retrieval.py / query_rewriter.py / adoc.py / case_store.py
```

**这个缺陷特别隐蔽：检索依然能命中「对的文件」，但给出的是旧实现，用户从答案里看不出来。**

修复：`ingest.py` 新增 `sync_codebase()`，建库前自动同步源码到副本目录，
就不存在「忘记同步」这种可能。

### 隐患二：自动化同步顺带引入了「评测集污染」

改成自动同步后，**评测立刻退化**：

| 域 | 修复副本之前 | 自动同步全部 `.py` 之后 |
|---|---:|---:|
| 官方文档域 文件级 | 83.3% | **66.7%**（-16.7pp） |

原因：同步范围一开始是「`app/*.py` + 根目录全部 `*.py`」，
于是 `eval_retrieval.py` 也进了知识库 —— **而它里面写着评测集的原文**：

```python
("Spring MVC 的 @RequestParam 注解是做什么的？",
 "spring-framework/.../requestparam.adoc", ""),
```

于是问「Spring MVC 的 @RequestParam 注解是做什么的」时，
**top-1 出处就是 `eval_retrieval.py` 里的 `DOCS_EVAL_SET` 那一行**。
实测 8 条未命中问题的 top4 里，评测脚本一共出现了 **8 次**。

**这是教科书级的「评测集污染」**：把答案（连同问题原文）放进了被评测的知识库。
更刺眼的是 —— 这个污染是**「改进」引入的**：
手工维护副本时只有 11 个核心文件，不含评测脚本；改成自动同步后才带进来。

修复：同步范围收窄为 `app/*.py` + 三个入口脚本
（`ingest.py` / `chat_cli.py` / `app_ui.py`），评测 / 抓取类工具脚本一律不入库。

> 这两个隐患合起来，正好是 ADR-011 那句「评测数字变好 ≠ 产品变好」的镜像版本：
> **评测数字变差，也未必是「系统变差」—— 它可能是数据管道被改坏了。**
> 而且两者的发现渠道不同：「副本过期」只有端到端能抓到（评测照样满分），
> 「评测集污染」则是评测抓到的。**两条路都要走。**

## 决策三：参数复扫 —— 数据分布变了，先验强度必须重扫

修完源码副本同步后，评测**立刻退化**：

| 域 | 副本过期时 | 同步为最新后 |
|---|---:|---:|
| 项目代码域 文件/符号 | 100.0% / 92.5% | 97.5% / 85.0% |
| 官方文档域 文件级 | 83.3% | **66.7%** |

**诊断**（`eval_audit.py` 的对照实验）：**关掉长尾先验，文档域立刻回到 83.3%**。
退化的全部来源就是这个先验。

**根因**：项目代码域扩容、且内容变了。ADR-011 扫出 `alpha=0.06` 时，
`data/codebase/` 只有 11 个**过期**文件；现在是 16 个最新文件，其中
`query_rewriter.py` / `retrieval.py` 这类模块的**长篇中文注释**里写着
「用户用中文问『FastAPI 怎么定义路径参数』时，`path-params.md` 排不进 top_k」——
这段中文与「中文提问官方文档」的语义高度重合。再加上长尾先验的加成，
问 FastAPI 时 **top-3 全被本项目代码的注释片段占满**：

```
问：FastAPI 的查询参数怎么声明和做校验？
1. [project] query_rewriter.py:1-29 · (module)      ← 本项目代码
2. [project] chain.py:101-119
3. [project] query_rewriter.py:33-46
4. [fastapi] query-params-str-validations.md        ← 正确答案垫底
```

**复扫**（`recall_k=96`，只跑线上链路）：

| alpha | 项目域 文件/符号 | 官方文档域 |
|---:|---|---:|
| 0.00 | 90.0% / 70.0% | 83.3% |
| **0.02** | **97.5% / 80.0%** | **83.3%** |
| 0.04 | 97.5% / 85.0% | 79.2% |
| 0.06（原值） | 97.5% / 85.0% | 75.0% |

**`alpha ≤ 0.02` 是「官方文档域满血」的边界**，0.04 起开始退化。
取 **`alpha = 0.02`** —— 在文档域不受损的前提下，让项目域拿到尽可能多的加成。

> **最大的教训：调参结果和数据分布是强绑定的。**
> `alpha=0.06` 曾经是扫出来的「双域甜点」，但那是**在一个过期且不完整的
> codebase 上**扫出来的。数据一变（哪怕只是「把副本修对」），
> 同一个参数就从最优变成了有害 —— 它会直接打掉文档域 16.7pp。
> **任何写进配置的魔数，都该标注它是在什么数据上扫出来的。**

| 域 | 策略 | 文件级 | 符号级 | 文件 MRR |
|---|---:|---:|---:|---:|
| 项目代码域（40 条） | 纯向量 | 95.0% | 77.5% | 0.875 |

| | 重排序 rerank | 100.0% | 85.0% | 0.869 |
| | **线上链路（最终）** | **97.5%** | **80.0%** | **0.823** |
| 官方文档域（24 条） | 纯向量 | 79.2% | — | 0.615 |
| | 混合检索 | 62.5% | — | 0.521 |
| | 重排序 rerank | 79.2% | — | 0.618 |
| | **线上链路（最终）** | **83.3%** | — | **0.649** |

> 项目代码域从上一版的 100%/92.5% 变成 97.5%/80.0%，**不是系统退化，而是基线变真实**：
> 此前知识库里的项目代码是**过期且不完整**的副本（缺 5 个模块），
> 现在它反映当前实现，代码片段从 45 涨到 94，片段之间的竞争自然更激烈。
> 官方文档域 83.3% 与修正口径后的水平一致。

## 本轮的五个教训

1. **「指标不动」和「指标变好」都可能是评测口径造成的，必须先做归因。**
   本轮拆解后才发现：数据清洗 0pp、口径修正 +12.5pp。
   不做这个拆分，任何结论都不可信。
2. **失败的检索项，要先去核对「标准答案」本身。**
   这次的顺序是：改算法（rerank，失败）→ 看数据源（发现空壳）→ 审标注（发现过窄）。
   **正确顺序应该反过来：先质疑答案，再质疑算法。**
   一个 96 字节的答案文件能骗过三轮算法优化，因为没人想过要去看它。
3. **同一个中间产物在不同环节的作用可能相反。**
   英文改写做检索 query 有效（关键词匹配），做 rerank query 有害（丢语义）。
   复用中间产物时不能想当然。
4. **改数据管道后必须重跑评测，并且一定要跑端到端。**
   「自动同步源码副本」是个纯粹的改进，却直接把文档域打掉 16.7pp；
   而更早那个「副本过期」的问题，评测是满分的、**只有端到端能发现**。
   **两条验证路径覆盖的是不同的失效模式，缺一不可。**
5. **调参结果和数据分布是强绑定的。**
   `alpha=0.06` 曾经是扫出来的「双域甜点」，但那是**在一个过期且不完整的
   codebase 上**扫出来的；数据一修对，它立刻变成有害参数。
   **配置里的每个魔数，都该标注它是在什么数据上、什么口径下扫出来的。**

## 遗留问题

- **残余 4 条属「跨框架概念重叠」**，需要领域路由 / 澄清追问等交互层设计，
  不是排序层能解决的。这两类问题恰恰是**用户最可能问的泛化问题**，
  优先级不低。
- **用户笔记与官方文档的定位冲突**：`data/langchain-核心概念.md`、
  `data/rag-实践笔记.md` 这类笔记归入 `project` 域、享受长尾先验加成，
  在「LangChain 概念」类问题上会压过官方文档。
  从产品角度未必是坏事（用户自己的知识沉淀优先呈现），
  但从评测角度需要明确它算不算「正确答案」。**先记下，不急着改。**
- **`MIN_BODY_CHARS` 是硬编码常量**，目前够用（任何真实文档都远超 200 字），
  若将来接入天然短内容的源（如 API 速查表）需要改成可配置。
