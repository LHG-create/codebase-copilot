# ADR-014：导语页治理、零重建清理，以及一个「评测跑的不是线上」的口径错误

- 状态：已采纳
- 日期：2026-10-17
- 相关：ADR-012（空壳文档与评测审计）、ADR-013（领域路由与澄清追问）

## 背景

ADR-012 修掉了「只剩 frontmatter 的空壳页」，但当时明确留了一个尾巴：

> 全库有 186 个小于 1000 字节的文件，其中 `dependencies.adoc`（474 字节的章节导语页）
> 已经被当成过标准答案。现在只挡住了「只剩 frontmatter 的空壳」，对「有正文、
> 但只是预告下一节」的导语页还没有判据。

本次要把这个尾巴收掉，同时把 `app/` 之外的两件事一起做掉：**索引清理不必重建**，
以及**评测必须跑线上那条链路**。

## 决策一：导语页用「整页占比」判定，而不是关键词命中

### 问题

Spring 的 `core/beans/dependencies.adoc` 全文 421 字符，正文只有一句：

> This next section explains how you go from defining a number of bean definitions
> that stand alone to a fully realized application where objects collaborate...

这句话一个字都没有讲「依赖注入怎么做」，但它的**语义向量与「依赖注入」极其接近**，
所以会稳定地排在真内容前面。它甚至一度是评测里「Spring 依赖注入」的标准答案，
而这个位置本该属于 `dependencies/factory-collaborators.adoc`（21 KB，标题就叫
`= Dependency Injection`）—— 这条评测从写下第一天就不可能通过。

### 尝试过的判据（第一版就错了）

第一版是「文里出现 `next section` 就算导语页」。干跑后发现两件事：

1. **误伤严重**：`solutions-to-common-problems.adoc` 里有一句
   "This section describes solutions to some common problems"，紧接着就是六个
   真实小节 —— 它是内容页，只是末尾随口说了一句「本节讲什么」。
2. **该抓的没抓到**：`dependencies.adoc` 反而漏了（当时阈值设得偏小）。

### 采用的判据

不是「命中关键词」，而是「**整页就是这句过渡语**」：

| # | 条件 | 挡掉什么误伤 |
|---|---|---|
| 1 | 正文长度 60 ~ 430 字符 | 489 字的 `mvc-freemarker.adoc`（真内容）被排除 |
| 2 | 无代码块、无表格 | 有代码就说明有实质内容 |
| 3 | 列表项 < 2 | `tutorial/security/index.md` 是 OAuth2 flows 列表，不该杀 |
| 4 | 段落数 ≤ 3 | 段落多说明有多个论述 |
| 5 | 命中导语句式的段落占正文 ≥ 45% | 只附带一句「详见下节」的内容页被放过 |

导语句式只认**指向别处**的说法：`this next section` / `the next sections?` /
`next chapters?` / `the following sections?` / `here you will see`。
刻意**不收** `this section describes` —— 那是在说本节内容，后面往往真有内容。

### 结果

在 10000 个片段上命中 **7 条**，逐条人工核对全部为真导语页。判据落在
`app/loader.py:looks_like_lead_in()`，与建库共用。

### 为什么只认这 7 条、不顺便把 186 个短文件都清掉

「小于 1000 字节」这个特征和「无检索价值」不是一回事：切分后的表格块、代码块、
真实的短小节都可能很小。**按长度砍是省事，但会连真内容一起砍。** 所以判据必须
基于内容语义，而不是文件大小 —— 这也是第一版脚本按**片段**长度判断、
把 AST 切出来的短代码片段全判成「空壳页」时踩到的坑。

## 决策二：索引清理不重建，按 id 删除

数据卫生规则修进 loader 后，只对「下次建库」生效。而当前这份索引里还躺着脏片段。

全量重建要重新调用近万次 embedding（费钱、几分钟），但这些文档是**可以精确识别**的，
所以直接按 id 从 FAISS 里删掉：

```bash
python prune_index.py            # dry-run，只报告会删什么
python prune_index.py --apply    # 真正删除并落盘
```

关键实现点：**判据不另写一套**，直接调用 `app.loader.exclusion_reason()`，
输入也是同一份整页原文。为此把「读文件 + 格式归一化」抽成了 `iter_source_texts()`，
让建库和体检走同一条读入路径 —— 两份实现迟早会漂移，而漂移的后果是
「建库放过的页面被体检误杀」。

本次实际删除 **1 条片段**（索引 10000 → 9999）。数量很小，但清理机制本身是可复用的：
下次改了卫生规则，不必再重建索引。

## 决策三：修一个「评测跑的不是线上」的口径错误

`eval_retrieval.py` 里叫「线上链路（最终）」的那一行，实际没开领域路由：

```python
# 错：Retriever 的 use_domain_route 默认是 False
online_retriever = Retriever(store, top_k=k, translator=make_cached_translator())
```

`Retriever` 自身默认 `False` 是有意的（诊断脚本要能跑「不带路由的纯检索」做对照），
但评测脚本忘了显式传 `True`。后果是这里测出官方文档域 **87.5%**，
而线上真实表现是 **95.8%** —— 差了 8.3pp，正好是一个「领域路由」的收益。

**这个错误比模型答错更隐蔽**：数字看起来很合理（比旧口径高，符合「逐步优化」的叙事），
不翻代码根本发现不了。已修，并在调用处写了注释说明为什么必须显式传。

修正后的评测结果（`top_k=4 / recall_k=96 / alpha=0.02`，9999 片段）：

| 域 | 纯向量 | 混合检索（对照） | **线上链路** |
|---|---:|---:|---:|
| 项目代码域 文件级 | 95.0% | 95.0% | **97.5%** |
| 项目代码域 符号级 | 77.5% | 72.5% | **80.0%** |
| 项目代码域 MRR | 0.875/0.677 | 0.871/0.642 | **0.879/0.673** |
| 官方文档域 文件级 | 83.3% | 62.5% | **95.8%** |
| 官方文档域 MRR | 0.625 | 0.521 | **0.747** |

未命中：项目域 1 条（`chat_cli.py` 的输入循环，问题里无任何线索，走全库）、
官方文档域 1 条（LangChain agent，根因是**改写质量**：正确片段在原问题路排第 3、
改写路掉到第 95）。prune 前后指标无变化 —— 删掉的 1 条片段本来也不在答案位。

## 后果

**好处**

- 数据卫生有了第二条判据，且建库/体检共用同一函数，不会各说各话。
- 改了卫生规则不必重建索引，`prune_index.py` 几秒钟就能同步。
- 「线上链路」这个标签重新名实相符。

**代价与遗留**

- 判据是按当前这批文档标定的（Spring / FastAPI 的写作风格）。换一批英文文档
  可能需要重标阈值 —— 它抓的是「写作习惯」而不是语法结构，这一点要诚实承认。
- 43 字以下的极小片段仍在索引里（表格块、代码块），未做处理。
- `README` 里的「186 个小于 1000 字节文件」这个说法容易误导：**数量不等于问题数量**，
  真正的脏数据只有 7 个导语页 + 已被挡掉的空壳页。
