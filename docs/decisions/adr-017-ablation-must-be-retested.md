# ADR-017：索引快照变化后，消融表必须整体重测

- 状态：已采纳
- 日期：2026-10-17
- 相关：ADR-011（长尾先验）、ADR-012（评测口径审计）、ADR-013（领域路由）

## 背景

ADR-011 里那张 2×2 消融表（查询改写 × 长尾先验）是在**旧索引快照**上测的：

- 当时全库 9956 片段，本项目代码 **82 片段（0.8%）**
- 表格结果：`92.5%/77.5%`（都不开）→ `100.0%/92.5%`（都开）

后来 `ingest.py` 改为建库前自动同步源码，重建索引后变成：

- 全库 10147 片段，本项目代码 **314 片段（3.1%）**

索引一变，片段之间的竞争关系就变了，**旧表格的绝对数字全部失效**。
但 README 的开头仍在用 `100%/92.5%` 做宣传，而同一份文件下方的评测表写的是
`97.5%/80.0%` —— 同一份 README 里两个数字打架。这是比「数字不好看」严重得多的问题：
面试官会认为整份文档的数字都不可信。

## 做法

1. 重跑 `eval_domain.py`，拿到 A（无改写无先验）、B（改写无先验）、C（改写+先验）三格；
2. 新增 `eval_ablation_cell.py` 补测缺失的第 4 格「无改写 + 长验」，让 2×2 齐全；
3. **两个域都跑**，不接受只看项目域的结论；
4. README 按新数据重写，旧数字只作为「历史注记」保留并标明来源。

## 结果（同一快照：10147 片段、`top_k=4`、`alpha=0.02`）

项目代码域（40 条）：

| 查询改写 | 长尾先验 | 文件级 | 符号级 | 文件 MRR |
|:---:|:---:|---:|---:|---:|
| ✗ | ✗ | 95.0% | 77.5% | 0.858 |
| ✓ | ✗ | 85.0% | 62.5% | 0.658 |
| ✗ | ✓ | 95.0% | 85.0% | 0.892 |
| ✓ | ✓ | **97.5%** | 80.0% | 0.769 |

官方文档域（24 条，同一组开关）：

| 查询改写 | 长尾先验 | 文件级 | 文件 MRR |
|:---:|:---:|---:|---:|
| ✗ | ✗ | 79.2% | 0.615 |
| ✓ | ✗ | 87.5% | 0.733 |
| ✗ | ✓ | **58.3%** | 0.354 |
| ✓ | ✓ | **87.5%** | 0.712 |

## 三个被新数据推翻/修正的结论

**① 旧结论「两者叠加超出各自之和」不成立。**

旧表里额外开一个开关都是正收益。新数据里「先验单独」在项目域符号级是 85.0%，
叠加改写后反而**降到 80.0%**（-5pp，2 条题）。两个机制不是互补放大，而是有取舍。

**② 新发现：长尾先验单独开，在文档域是灾难。**

`79.2% → 58.3%`，掉了 20.9pp。原因很直接：先验会把中文源码片段强行往前提，
而文档域问的都是英文官方文档。这个机制**天生依赖跨语言改写**去平衡。

如果不跑文档域，只看项目域，会得出「先验单独开就够，还能省掉一次 LLM 改写调用」的
错误结论 —— 而且这个结论在项目域的数据上完全说得通。

**③ 叠加的真实收益不是「双赢」，是一笔明确的交换。**

相比「只开先验」：项目域符号级 -5pp，换文档域 +29.2pp（58.3% → 87.5%）。
决策依据是用途权重：文档域是主场景（问框架怎么用），项目域的损失落在 2 条题上。

## 教训

1. **任何基于索引的对照实验，都与快照绑死。** 重建索引后，历史表格里的绝对数字
   一律视为失效，要么重跑，要么显式标注「旧快照，仅供对照」。
2. **一个开关的效果必须至少在两个域上看。** 本项目已经用这条原则否掉过 rerank
   （项目域 +5pp / 文档域 -4.1pp），这次又否掉了「先验单独开」。
3. **README 内部的数字自洽，比单个数字好看更重要。** 这次是「靠人读出来」的，
   没有自动化检查兜底 —— 属于已知的流程缺口。

## 复现

```bash
python eval_domain.py        # A/B/C + alpha 扫描 + 语义路由对照
python eval_ablation_cell.py # 补全 2×2 的「无改写 + 先验」一格
```
