# ADR-011：跨领域干扰与「长尾领域」先验重排

- 状态：已采纳
- 日期：2026-10-15

## 背景

ADR-010 末尾留了一个未解问题：知识库从 4 个框架（4385 片段）扩到 6 个框架
（9956 片段）后，评测集（40 条，全部问本项目源码）指标从
**文件级 97.5% / 符号级 87.5%** 掉到 **92.5% / 77.5%**，
并且实测出现了「问 Spring 的注解，FastAPI 的文档挤占召回位」的现象。

当时给出的方向是「按领域分库 / 检索前先做文档路由」。本 ADR 记录实际做的诊断、
尝试过并放弃的方案，以及最终采纳的做法。

## 诊断一：量化领域不均衡

| 领域 | 片段数 | 占比 |
|---|---:|---:|
| Spring Framework | 3591 | 36.1% |
| Spring Boot | 1959 | 19.7% |
| Vue.js | 1324 | 13.3% |
| LangChain | 1146 | 11.5% |
| FastAPI | 1071 | 10.8% |
| LangGraph | 779 | 7.8% |
| **本项目代码** | **82** | **0.8%** |

**近万片段里，本项目代码只占 0.8%。** 而评测集 40 条全部问的是本项目源码。

## 诊断二：零干扰对照

把检索范围**限制在「本项目代码」子库（82 个片段）**里，跑同一套评测集：

| 检索范围 | 文件级 | 符号级 |
|---|---:|---:|
| 全库（9956 片段） | 92.5% | 77.5% |
| **仅项目子库（82 片段）** | **97.5%** | **87.5%** |

「仅项目子库」的成绩与库扩容**之前**的记录完全一致。

> **结论：跨领域干扰就是唯一原因。** 不是检索算法退化，也不是切分质量问题。
> 先证明问题在哪，再动手 —— 这一步省下了后面大量的盲目试错。

## 探索：三条被证伪 / 受限的路

### 1. 质心语义路由（❌ 证伪）

**思路**：给每个领域算一个「质心向量」（该领域全部片段向量的平均方向），
用问题向量与各质心做余弦相似度判断领域，再去对应子库检索。
诱人之处在于成本极低：质心可以直接用 faiss 的 `reconstruct_n` 从**已建好的索引**
里现算，零 embedding 调用、零重新建库。

**实测：判定准确率只有 26/40 = 65%。**

| 问题 | 判成 | 真实领域 |
|---|---|---|
| 「RAG 问答链是怎么把检索和生成串起来的？」 | 其他 | 本项目代码 |
| 「RagAssistant 类的整体职责是什么？」 | LangChain | 本项目代码 |
| 「构建 assistant 的入口函数是什么？」 | LangChain | 本项目代码 |
| 「API Key 是怎么和 provider 对应起来的？」 | FastAPI | 本项目代码 |

根因很清楚：**本项目代码本身就是用 LangChain 写的**，docstring 与注释里
全是 LangChain 术语，质心根本分不开「本项目的 chain.py」和「LangChain 官方文档」。
拿它去硬路由，指标直接掉到 **65.0% / 55.0%（-27.5pp）**。

> **教训：查询侧硬路由，判定错误时代价是全盘皆输。**

### 2. 领域多样性硬配额（❌ 放弃）

**思路**：最终 top_k 里限制单一领域最多占 2 席，保证小领域有出场机会。
**实测：-2.5pp。** 因为正确答案本身常常就是**同一领域的多个片段**（比如一个被
切成 3 块的表格），硬配额会误伤它们。

### 3. 代码符号精确通道（△ 保留，作用有限）

**思路**：问题里出现 `_CodeUnit` / `format_docs` 这类符号时，
直接按 `metadata.name` 精确召回并提权。
**实测：MRR 0.833 → 0.850**（排得更靠前），但**命中率没有变化** ——
40 条问题里只有 17 条含显式符号，而恰恰是**不含符号的那几条**
（如「网页界面是怎么渲染出处的？」）才真正需要帮助。

## 决策：长尾领域先验重排

放弃「判断问题属于哪个领域」，改为**按领域规模做逆频率加权**：

```
prior(领域) = alpha × log(总片段数 / 该领域片段数) / log(总片段数)
   —— 仅当该领域占比 ≤ rare_ratio（默认 5%）时生效

排序分 = RRF 融合分 + prior(领域)
```

直觉：**能在海量大领域里挤进候选的长尾片段，本身就更值得看。**
这与 BM25/IDF 里「稀有词权重更高」是同一个思想，只是把「词」换成了「领域」。

与硬路由的本质区别：**它是加权，不是过滤。** 硬路由判错 → 正确答案所在领域
根本没被检索，全盘皆输；加权判错 → 最坏退化成原来的全局检索。

### 为什么必须限定 `rare_ratio`（这是最关键的一次修正）

不加限制时（`rare_ratio=1.0`），先验表是：

| 领域 | 占比 | 先验 |
|---|---:|---:|
| 本项目代码 | 0.8% | +0.0310 |
| LangGraph | 7.8% | +0.0017 |
| FastAPI | 10.8% | +0.0015 |
| Spring Framework | 36.1% | +0.0007 |

于是 **FastAPI 拿到的先验高于 Spring Framework**。跑评测时一切正常
（官方文档域甚至涨到 75.0%），但**端到端真机验证抓到了问题**：

> 问：「Spring MVC 里 `@PathVariable` 和 `@RequestParam` 有什么区别？」
> top-4 结果：`FastAPI/query-params.md` × 4
> 模型回答：「根据已有资料无法回答该问题」（直接拒答）

先验本该用于纠正「0.8% vs 99.2%」这种**极端**失衡，
一旦让它在中等领域之间重新分配权重，就只是**用一个新的偏差替换掉旧的**。

修正后只对占比 ≤5% 的领域加权：

| 配置 | 项目域 文件/符号 | 文档域 文件级 | Spring 跨领域问题 |
|---|---|---|---|
| `alpha=0.06, rare=1.0` | 100% / 92.5% | 75.0% | ❌ top-4 被 FastAPI 占满 |
| `alpha=0.06, rare=0.10` | 100% / 92.5% | 66.7% | ✅ 正常 |
| **`alpha=0.06, rare=0.05`** | **100% / 92.5%** | **70.8%** | ✅ 正常 |

**限定 `rare_ratio=0.05` 后，项目域的收益一分没少，同时消除了真实用户可见的失败。**
代价是文档域回落到基线 70.8% —— 但那 +4.2pp 本来就来自错误的权重再分配，不要也罢。

### 另一个容易踩的坑：「杂项」领域不该吃红利

最初把 `data/` 根目录下的两份项目笔记归进了 `other`（杂项）领域。
结果 `other` 片段数最少，拿到的先验**比本项目代码还高**，在检索项目问题时抢占召回位。
修正：`data/` 下的笔记（本项目自己的学习笔记）归入 `project`。

## 参数选择

`recall_k`（单路召回池宽度）与 `alpha` 的二维扫描（项目域 / 文档域，文件级）：

| recall_k | alpha | 项目域 文件/符号 | 文档域 文件级 |
|---:|---:|---|---|
| 32 | 0.02 | 92.5% / 82.5% | 75.0% |
| 64 | 0.06 | 97.5% / 90.0% | 75.0% |
| **96** | **0.06** | **100.0% / 92.5%** | 75.0% |
| 96 | 0.13 | 100.0% / 92.5% | 66.7% ⚠️ |
| 128 | 0.06 | 97.5% / 90.0% | 75.0% |

两点观察：

1. **`alpha=0` 时加大 `recall_k` 反而更差**（96 → 87.5%）。池子变大本身会引入噪声，
   必须配合先验重排才能变废为宝。
2. **`recall_k=32` 时先验起不了作用**（92.5%），因为池子里根本没有足够多的
   长尾候选可供挑拣。

**采用 `recall_k = 96`、`alpha = 0.06`、`rare_ratio = 0.05`**，写进 `Settings` 便于调参。

## 效果

双域评测集（项目代码 40 条 + 官方文档 24 条），`top_k=4`。

### 消融实验：查询改写与长尾先验各自的贡献

| 查询改写 | 长尾先验 | 项目域 文件级 | 符号级 | 文件 MRR |
|:---:|:---:|---:|---:|---:|
| ✗ | ✗ | 92.5% | 77.5% | 0.833 |
| ✓ | ✗ | 87.5% | 70.0% | 0.677 |
| ✗ | ✓ | 97.5% | 87.5% | 0.902 |
| **✓** | **✓** | **100.0%** | **92.5%** | **0.952** |

这张表里有三个值得注意的事实：

1. **查询改写单独用在项目代码域是负优化**（92.5% → 87.5%，MRR 0.833 → 0.677）。
   它引入的英文改写路会带来一批语义相近的英文文档片段，稀释了中文源码片段的排名。
   （这和 ADR-006 的结论不矛盾：ADR-006 针对的是**长口语化提问**，
   而评测集是短问题，改写收益本来就小、噪声反而更明显。见「遗留问题」。）
2. **长尾先验单独用是正优化**（92.5% → 97.5%，MRR 0.833 → 0.902）。
3. **两者叠加优于各自单独使用**（100% / 92.5%）：先验恰好能把被英文路稀释掉的
   源码片段重新提上来，两者形成互补。所以最终两个开关都保持开启。

### 官方文档域

| 查询改写 | 长尾先验 | 文件级 | 文件 MRR |
|:---:|:---:|---:|---:|
| ✗ | ✗ | 70.8% | 0.552 |
| ✓ | ✗ | 70.8% | 0.566 |
| ✗ | ✓ | 70.8% | 0.479 |
| ✓ | ✓ | 70.8% | 0.462 |

**命中率完全不动（70.8%），MRR 有 ±0.09 的波动。**

这个「不动」本身就是结论：本次的两个机制都是**针对长尾偏差的定向修补**，
不是普遍性的检索质量提升。官方文档域的真正瓶颈是**跨语言语义匹配本身**
（中文问题 vs 英文文档），那是另一个问题，需要换多语言向量模型或加强改写来解决。
**至少可以确认：为提升项目代码域所做的改动，没有牺牲官方文档域。**

## 附带收获：评测与实现脱节

做这次分析时发现一个更要命的问题：

**老评测跑的是「纯向量 top-k」，而线上跑的是「中文改写 + 双路 RRF」。**
两者不是一条链路，后果是：

- 评测看不出查询改写的价值（它压根没走改写）
- 线上真实效果没有数字支撑
- 想优化时不知道该优化哪一段

**改法**：把检索链路抽成独立模块 `app/retrieval.py`，
`chain.py` 和评测脚本 import 的是同一个类。评测跑的就是线上链路。

顺带新增**官方文档域评测集**（24 条，覆盖 FastAPI / Spring / Vue / LangChain /
LangGraph），因为只在一个域上调参极易「把一个域做上去、另一个域做塌」。
它立刻暴露了一个此前完全没被量化的事实：
**中文问题检索英文文档本身只有 70.8% 的命中率** —— 这是下一个改进点。

还有一条更实在的经验：**评测数字变好 ≠ 产品变好**。
`rare_ratio=1.0` 那一版评测数字最漂亮，却是唯一会让模型对 Spring 问题拒答的版本。
**双域评测 + 端到端真机抽查，缺一不可。**

## 取舍与风险

- **先验只救长尾，不干预主流领域之间的排序。** 这是被真实失败逼出来的设计约束，
  也意味着它无法改善「Spring 与 FastAPI 谁该赢」这类问题 —— 那属于语义检索本身的
  能力边界，应该交给重排序模型（rerank）而不是靠权重硬掰。
- **参数是在 64 条评测集上扫出来的**，存在过拟合风险。缓解方式是两个域同时看，
  并避开 `alpha` 的退化边界取值。
- **多了一次领域统计的启动开销**（遍历 docstore，约 1 秒），
  通过 `docstore._dict` 快路径 + 实例内缓存压到可接受范围。

## 遗留问题

- **查询改写的价值需要更贴近真实的评测集来验证。**
  本评测集是短问题（「FastAPI 里怎么声明路径参数？」），语义本就清晰，改写收益小、
  噪声反而明显；而 ADR-006 的定性证据来自长口语化提问
  （「Spring MVC 里 @PathVariable 和 @RequestParam 有什么区别？
  路由 `/users/{id}` 的参数该用哪个？」）。
  下一步应当补一组「口语化长问题」评测项，用数据回答改写到底该不该默认开启。
  **在没有这组数据之前，不做结论** —— 这正是本次学到的：指标口径决定了你能看到什么。
- **官方文档域 70.8% 是当前最明显的短板**，瓶颈在跨语言语义匹配本身，
  需要换多语言向量模型或更强的改写策略。

## 影响

- 新增 `app/domain.py`：领域识别、质心与子库（诊断/对照用）、领域先验权重
- 新增 `app/retrieval.py`：检索链路（查询改写 → 双路 RRF → 长尾领域先验重排），
  `chain.py` 改为调用它
- 评测升级为**双域**：`eval_retrieval.py`（最终链路 vs 旧口径），
  `eval_domain.py`（诊断与参数扫描）
- `Settings` 新增 `recall_k=96`、`domain_prior_alpha=0.06`、`domain_prior_rare_ratio=0.05`
- 前端出处卡片显示领域标签
