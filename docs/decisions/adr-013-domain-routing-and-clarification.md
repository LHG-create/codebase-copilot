# ADR-013：不是排序不够好，是问题没说清

- 状态：已采纳
- 日期：2026-10-16

## 背景

ADR-012 收尾时留下一句判断：

> 「修正口径后仍有 4 条未命中（CORS、依赖注入、agent、RAG），根因是同一个概念在
>   多个框架 / 多个页面下都有文档，检索无法判断用户问的是哪一份。这类泛化问题
>   恰恰是用户最常问的，但它不是排序层能解决的 —— 需要交互层设计。」

这一轮就是去做交互层的。但动手前先重新诊断了一次，**发现那句判断只说对了一半**。

## 第一步：重新诊断 —— 4 条失败其实是两种病

对 4 条未命中项，把「当前链路 top4」「英文路候选池的领域分布」「正确片段在池中的排名」
逐条打出来：

| 未命中项 | 正确片段在候选池的排名 | 当前 top4 的构成 | 病在哪 |
|---|---:|---|---|
| FastAPI 怎么配置跨域 CORS？ | 英文路 **#1** | 全被 Spring 的 `webflux-cors` 占满 | **排序层**：召回了却排不进 |
| Spring 的依赖注入有哪几种方式？ | 两路都没有 | Spring 系的其他页面 | **数据层**：答案标错了（见第五步） |
| LangChain 的 agent 是怎么工作的？ | 两路都没有 | langgraph + langchain 其他页 | **召回层**：根本没进来 |
| LangChain 怎么做检索增强生成 RAG？ | 英文路 #37 | 全是 project 域的笔记 | **排序层**：被先验顶上来的笔记压住 |

**「FastAPI CORS」这条最刺眼**：正确答案在英文路排第 1，说明召回完全没问题；
它之所以掉出 top4，是因为跨域 RRF 融合时，Spring 的 `webflux-cors.adoc`
在中文路和英文路都排得很靠前，两路共识把它推了上去。

这不是「语义不够好」，而是**问题本身就缺了一个关键信息：问的是哪个技术栈**。

## 第二步：语义路由 —— 再次被证伪，而且更彻底

`app/domain.py` 里早就写好了「领域质心向量路由」（用每个域全部片段向量的平均方向
判断问题属于哪个域），但一直没接线。先把它接上试：

| 域 | 基线（全局检索） | 语义路由 | 差异 |
|---|---:|---:|---:|
| 项目代码域 文件级 | 97.5% | **65.0%** | **-32.5pp** |
| 项目代码域 符号级 | 80.0% | 55.0% | -25.0pp |
| 官方文档域 文件级 | 87.5% | 83.3% | -4.2pp |

**崩得很彻底。** 原因很直白：本项目代码本身就是用 LangChain 写的，
`retrieval.py` 里满是「检索」「片段」「召回」这类词，与 langchain 域的质心几乎重合。
质心分不开「讲检索的本项目代码」和「讲检索的 LangChain 官方文档」。

> 这一条其实 ADR-011 就用 D 组对照做过初判，本轮把它做成了完整评测。
> `route_query` 因此**保留但不再接入线上**，只作为证据留在代码里。

## 第三步：显式线索路由 —— 认，而不是猜

语义路由失败的根因是「它试图从内容里**推断**领域」。但回头看第一张表，
4 条问题里**全都直接写了框架名**：

- 「**FastAPI** 怎么配置跨域 CORS？」
- 「**Spring** 的依赖注入有哪几种方式？」
- 「**LangChain** 的 agent 是怎么工作的？」

用户根本不需要被推断 —— 他已经在问题里说清楚了。所以正确做法是**认**：
从问题里抽取显式线索（框架名 / 本项目自称 / 本项目代码符号），
线索唯一命中时，把检索限定到该领域内。

实现落在 `app/domain_router.py`，检索侧在 `Retriever` 里接一个子库切换。
先做了一次「域内硬切 vs 候选池软过滤」的对照：

| 策略 | 5 条疑难问题命中 |
|---|---:|
| 当前链路（全局） | 1/5 |
| 候选池软过滤（挑出域内候选） | 3/5 |
| **域内硬切（在子库里检索）** | **4/5** |

**软过滤反而不如硬切**，原因值得记下来：软过滤是在「跨域 RRF 融合后」的池子里挑域内
候选，跨域竞争已经发生过了；而硬切是让该域的语料**独占**一次 top-k，
别的域根本不参与排序 —— 跨领域干扰被物理消除。

路由判定的准确率：**38/38（100%）**。官方文档域 24 条问题全部带框架名且全部判对，
项目代码域 40 条里 14 条带线索、也全部判对。

## 第四步：加权 RRF —— 一个被 top_k 坑掉的「好主意」

域内检索时，「LangChain 的 agent」仍然失败。查下去发现：

```
问题: LangChain 的 agent 是怎么工作的？
改写: agent workflow reasoning action observation   ← 关键词堆砌
中文路正确片段排名: 3      ← 原问题本来就能命中
英文路正确片段排名: 95     ← 改写把它推到了第 95 位
```

改写质量太差，等权 RRF 求和后被噪声挤掉。于是推论：「原问题是用户真实意图，
改写是有损派生，应当降低改写路权重」。

**在 `top_k=8` 的快速试验里，它看起来完全正确** —— 降到 0.5 后两域都没退化，
那条 agent 问题也被救回了。于是写进配置。

但用完整评测（`top_k=4`、两个域）复跑：

| 域 | 等权（采用） | 加权 0.5 | 差异 |
|---|---:|---:|---:|
| 官方文档域 文件级 | **95.8%** | 91.7% | **-4.1pp** |
| 项目代码域 文件级 | **97.5%** | 95.0% | **-2.5pp** |

**净负优化** —— 用「救回 1 条」换了「丢掉 3 条」。

原因：`top_k` 越小，越依赖两路共识来拉开差距；压低其中一路，反而让排序变糊。
在 `top_k=8` 下多一条容错空间，问题被掩盖了。

> **教训**：小样本 + 宽松 top_k 上的「有效」，在大 top_k 压力测试下可能是负的。
> 参数默认值已改回等权（`rewrite_weight=1.0`），这一项作为**第二次证伪**
> 保留在配置里，附完整的证伪说明。

## 第五步：又一处「标准答案是导语页」

「Spring 的依赖注入」两路都召不回，查下去发现标准答案 `dependencies.adoc`
**只有 474 字节**，正文是：

> This next section explains how you go from defining a number of bean definitions
> that stand alone to a fully realized application…

这是 Spring 文档的**章节导语页**，只有「接下来讲什么」，没有任何 DI 内容。
真正讲构造器注入 / Setter 注入的是同目录下的 `factory-collaborators.adoc`，
标题就叫 **`= Dependency Injection`**，21598 字节。

**这和 ADR-012 抓到的 `retrieval.md` 空壳是同一族问题**，而且更隐蔽 ——
`retrieval.md` 是 96 字节的空壳，被 `MIN_BODY_CHARS=200` 挡住了；
`dependencies.adoc` 有 474 字，刚好越过阈值，混进了库。

顺手全库扫了一遍：**186 个文件小于 1000 字节**（含已被 `nav-*` 规则排除的导航页）。
「导语页 / 目录页污染」是个系统性隐患，本轮只修正了 `dependencies.adoc` 这一处标注，
不扩大改动范围。

## 第六步：认不出来的时候，问

线索唯一命中就路由，那**线索指向多个领域时怎么办**？

答案是**不猜，问** —— 这就是「澄清追问」。判定规则：抽取出 ≥2 个不同领域线索时，
不生成回答，而是返回候选项让用户点选。

理由是不对称的代价：

- **猜对**：只是略快一点。
- **猜错**：给出错误技术栈的答案，而且**用户很难察觉** ——
  Spring 的 CORS 配置和 FastAPI 的完全是两回事，但两段答案「看起来都对」。

行为验证（用探针问题，因为评测集里的问题只带单一框架名，覆盖不到歧义分支）：

```
[触发澄清]       Spring 和 FastAPI 的依赖注入有什么区别？
[触发澄清]       LangChain 和 LangGraph 有什么区别？
[触发澄清]       Vue 和 Spring 各自怎么处理请求？
[无线索->全局]   怎么配置跨域 CORS？
[路由到 project] 本项目的检索链路是什么？
```

## 最终指标（top_k=4，两次修正口径后）

| 域 | 指标 | 基线（无路由） | 领域路由 | 语义路由（对照） |
|---|---|---:|---:|---:|
| 项目代码域 | 文件级 | 97.5% | **97.5%** | 65.0% |
| | 符号级 | 80.0% | **80.0%** | 55.0% |
| | 文件 MRR | 0.823 | **0.879** | 0.608 |
| | 符号 MRR | 0.625 | **0.673** | 0.460 |
| 官方文档域 | 文件级 | 87.5% | **95.8%** | 83.3% |
| | 文件 MRR | 0.691 | **0.747** | 0.628 |

- 官方文档域 **+8.3pp**，两个域的 MRR 都提升（项目域文件级持平，但排序更靠前）。
- 线索判定 **38/38 全对**。
- 官方文档域基线上涨（83.3% → 87.5%）来自第五步的标注修正，**不是系统改进** ——
  这个区分是 ADR-012 留下的习惯，继续沿用。

## 决策

1. **接入显式线索路由**，默认开启（`Retriever.use_domain_route=True`）。
2. **线索指向多个领域时澄清追问**，不猜。
3. **语义路由（质心）不接入**，`route_query` 保留作对照证据。
4. **加权 RRF 不采用**，`rewrite_weight` 默认 1.0。
5. 修正 `dependencies.adoc` → `factory-collaborators.adoc` 的评测标注。

## 后果与遗留

- **收益是真的，但要说清来源**：+8.3pp 里只有一部分是「路由」的功劳，
  另一部分来自第五步的标注修正。分开记账。
- **残余未命中 2 条**：
  - 「命令行问答怎么循环接收用户输入？」（无线索、走全局，与本次改动无关）
  - 「LangChain 的 agent 是怎么工作的？」（`top_k=4` 下域内 RRF 仍把它挤出；
    它在原问题路排第 3，是**改写质量**问题，不是路由问题）
- **「澄清」的触发面偏窄**：只有显式提到多个框架才会触发。真实用户更常见的形态是
  「依赖注入怎么用」（一个线索都没有）—— 这类问题走全局检索，实测项目域 39/40，
  语义检索在无框架名干扰时是可靠的，因此**刻意不做过度澄清**（会打断用户）。
  是否要引入「检索结果跨域分散时给柔性提示」，留待观察。
- **导语页 / 目录页污染**尚未系统治理（全库 186 个 <1000 字节文件）。
